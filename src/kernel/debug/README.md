Kernel debugging fragments live here, including COM1 debug tracing, debugger commands, exceptions, and graphical debugger UI.

- `serial.c` - COM1 tracing plus the RAM mirror of the trace that `bootlog.c` persists.
- `bootlog.c` - the on-medium `bios-serial.log` file for real hardware: the kernel locates the boot medium's FAT12/16 volume (MBR -> BPB -> root dir -> the file's cluster chain -> a hidden tail stamp), then auto-saves new trace sectors into the file continuously and does a final complete flush at power off, restart, halt and from the crash handler (polled ATA for the disk image; a bare-metal firmware/USB disk is read through INT 13h for validation and written through the same path only on the drive the loader booted from, while a hypervisor boot stops after the graphics mode is set). Discovery follows the drive the loader booted from, never "the first disk with a template", and an early save before the video mode set leaves a trace even if the mode set hangs. Staged checkpoints cover graphics init, the first frame, the self-test, the IRQ0 probe and main-loop entry. The boot menu also shows a compact `LOG ...` status line (raw `boot_device`, parsed drive, `INT13 0xNN`/`INT13 0xNN chs`/`ATA`, bytes saved, and a reason such as `INT13 read failed`, `no log volume`, `INT13 ext/CHS absent`, `realmode window busy`, `firmware disk: not boot drive` or `write failed`) so a machine without COM1 still reports why the file stayed empty. When a firmware boots USB in legacy mode but exposes no AH=41h/42h/43h extended services, the writer queries the drive geometry with AH=08h and uses the legacy AH=02h/03h CHS read/write path instead; ` chs` in the status line says that fallback is the active path. Row 14-19 of the boot menu carry the bring-up panel: one `INT13 0xNN ...` line per probed firmware disk (`ext ok`, `ext AHxx`, `ext Fxx`, `chs`, `rd`, `LOG YES` only when the hidden stamp validated), a PCI `USB ...` inventory and a `BRIDGE ...` line with the real-mode stack size and the post-call IVT check. Discovery never issues the AH=00h reset (it can wait for a masked IRQ), passes a real buffer to AH=41h, and scans 0x80-0x87 so a stale reported drive number does not hide the stick. `realmode.asm` restores the firmware IVT after every call and runs on a 32 KB validated stack; both were required for real firmware whose disk handler chains INT 08h or whose USB-legacy keyboard injects through INT 09h. When port 0x60 stays silent, `keyboard_mouse.c` reads the firmware's INT 16h buffer instead (`bios N` on the input line); `make BIOS_KBD_FORCE=1` forces that path for bring-up. The file is a plain FAT file the host sees with no extraction step.
- Native xHCI HID input (USB-only machines): `../driver/input/xhci_hid.c` normally adopts the firmware-configured boot-keyboard interrupt endpoint on a running controller, leaves CRCR/interrupter 0 alone, and uses a private event ring on interrupter 1 (or endpoint-dequeue polling when the controller has only one interrupter). If a hard reset left no HID endpoint, the boot check flushes the trace, detaches the medium and calls `xhci_boot_recover()`, which resets the controller and enumerates root ports itself. Boot menu row 20 prints the live state (`XHCI bb:ss.f run HID evt1 slot N ep M keys K`), and the `USB ...` line switches from `(no HID driver)` to the live controller. `keyboard_mouse.c` bounds the 8042 drain and skips it once the native path is live, so a floating status port (`0xFF`) cannot spin the main loop.
- `exceptions.c` + `../system/interrupts.asm` - the crash path. `isr_common_stub` copies the CPU frame onto a dedicated 16 KiB crash stack before the first C push, so a stack fault or a corrupted ESP still produces a report instead of a triple-fault reset. `cpu_exception_handler` paints the BSOD first and flushes the boot log after it (a polled ATA flush can block behind a dead disk and must never hide the screen), and `crash_guard_call()` runs each paint pass with an assembly recovery point: a fault while drawing returns -1 and falls back to the compact report (no memory map), the VGA text report, or the cube animation, instead of retrying a broken renderer forever. A nested fault outside the guard never redraws. `#BP`/`#OF` are logged and returned through `iretd`, so an `int3` continues instead of stopping the machine. The EBP walk is compiled into both profiles (both keep frame pointers): release builds draw the raw return addresses under the memory map, debug builds resolve them through the generated symbol table and open the interactive viewer.
- `debugger.c` - the Ctrl+Shift+Enter debug terminal (its `crash` command is also the quickest way to exercise the boot-log flush).
- `render.c` - the graphical debugger UI rendering.
